# 自然语言操作业务系统：方案、取舍与反思

目标：把"只能查询的数据分析 Agent"升级为"能用自然语言**操作**业务系统的小型 Web 系统"，并能作为面试现场的可运行演示。

## 1. 调研结论（决定了设计）

| 来源 | 结论 | 我们怎么用 |
|---|---|---|
| [Smashing: Designing for Agentic AI](https://smashingmagazine.com/2026/02/designing-agentic-ai-practical-ux-patterns/) | 写操作前要有 **Intent Preview**；高风险动作要 **Action Audit & Undo**；不确定时要 **Escalation** | 提案卡片（预览真实参数）、审计时间线、撤销（reverse）、拒绝时给出原因 |
| [LangChain 前端 HITL 文档](https://docs.langchain.com/oss/python/langchain/frontend/human-in-the-loop) | 审批卡展示 `name / args / description`；按钮由 `allowedDecisions` 决定；拒绝要有原因输入；中断随 checkpoint 持久，刷新后仍在 | 审批卡同款字段；决定带 note；待办状态存库，刷新不丢 |
| [AI UX: Suggest / Confirm / Execute](https://www.aiuxplayground.com/pattern/suggest-confirm-execute) 及 AWS Agentic AI Lens | 审批卡必须展示**真实载荷**而不是摘要；只给高风险写操作加闸，读操作放行（否则审批疲劳）；"终端用户即审批人"适合同步暂停，"独立审批人"适合异步回调 | 读明细数据 = 同步暂停（已有）；写业务状态 = 异步多签工作流（新增） |
| 开源产品：Wren AI、SQL Chat、Vanna、LangChain agent-chat-ui | 都是"聊天 + 结果表格 + 流式"；agent-chat-ui 是 Next.js，绑定 LangGraph Platform 协议，与我们的 `/v1/tasks` 接口不兼容 | 前端自己写，**无构建步骤的单页**（原生 JS + SSE），一条命令能跑 |

## 2. 功能边界

做：
1. **退款**这一条完整的业务写流程（`refundPolicy.md` 里已有分级审批规则，业务真实、规则现成）：提案 → 校验 → 按金额分级多签 → 生效 → 可撤销，全程留痕。
2. Agent **只能提出申请，不能执行**。申请之外的一切（批准、驳回、冲销）只能由持有角色令牌的人通过 HTTP 接口完成。
3. 前端单页：聊天、过程时间线、预算仪表、审批收件箱、审计页、演示角色切换。

不做（写进限制，不假装）：
- 不做通用 CRUD，不让模型写 SQL 修改数据；只有一个窄的、带类型的写函数。
- 不做区域经理按区域授权、不接 SSO；角色只是演示级令牌。
- 不做"退款后净收入"视图，不改 `sales` 表（避免影响 61 条评估基线）。
- 不接真实支付；"生效"= 业务库状态变更。
- 记忆（mem0）没有界面入口。

## 3. 关键设计与取舍

**Agent 无写能力。** 工具 `propose_refund` 只会写一行 `pending` 的申请；真正的批准在 `POST /v1/refunds/{id}/decision`，身份来自 token，不来自请求体，更不来自模型。即使提示词被注入，模型也没有"批准"这个动作可调用。

**规则由代码强制，不靠提示词。** 订单存在、金额不超过订单额、30 天窗口、同一订单只能有一笔有效退款（唯一索引）、申请人不能审批自己的申请（职责分离）、金额决定需要哪些角色签字。模型传来的参数一律当作不可信输入。`service_outage_over_72h` 是模型转述的客户说法，卡片上标注"待审批人核实"。

**两类审批，两种机制，因为风险类型不同：**
- 读机密明细：申请人本人在场，Agent 同步暂停，用已有的 `interrupt` + checkpoint。
- 写业务状态：审批人是另一个人，异步，状态存业务库，多签。

**写入路径与只读路径隔离。** `sql_guard` 依旧只读；写入用单独的模块和连接，只暴露 `propose / decide / withdraw / reverse` 四个函数，没有"执行任意 SQL"的入口。SQLite 单写者 + `BEGIN IMMEDIATE`，决定操作是原子的。

**默认关闭。** `ENABLE_ACTIONS=0` 时工具不挂载、提示词不变，61 条评估基线不受影响。演示使用 `data/demo.db`（`test.db` 的副本），不动被 git 跟踪的 `test.db`。

**业务日期可配置。** 数据在 2026-01 至 06，真实日期早已超过 30 天窗口；用 `BUSINESS_DATE` 固定"今天"，否则演示里所有退款都会被判为超期。

## 4. 用户、交互与功能入口

三类使用者，三种主交互：

| 使用者 | 想要什么 | 主交互 |
|---|---|---|
| 提需求的人（alice） | 说一句话把事办了；知道系统在干什么、花了多少；知道申请到哪一步 | 底部输入框 + 示例按钮；回答卡片里的过程时间线和申请卡 |
| 审批人（bob / carol / dave） | 一眼看清要批什么（真实金额、依据、谁已签）；批或驳回；事后可查 | 顶部"待处理"收件箱；详情卡上的批准 / 驳回 / 冲销 |
| 管理员（root） | 谁花了多少、哪个工具总出错、发生过什么 | 顶栏用量仪表 → 用量看板；"审计"页 |

每个功能必须有入口，没有入口的功能等于没有：

| 功能 | 入口 | 状态 |
|---|---|---|
| 自然语言提问 / 查询 / 分析 | 输入框；示例按钮（分四组：分析、读明细、写操作、护栏） | 做 |
| 过程可见（分流 → 简报 → 研究 → 报告；每次 SQL / 工具调用） | 回答卡片里的"过程"，流式更新 | 做（新增 tool/usage 实时事件） |
| token / 费用 / 日预算 | 顶栏仪表，任务运行中实时增长；点开看 7 天 | 做 |
| 预算耗尽 / 限流 | 输入框上方条幅，带倒计时 | 做 |
| 停止任务 | 运行中回答卡片的"停止" | 做 |
| 历史任务 | 左侧栏 | 做 |
| 幂等重复提交 | 自动带 Idempotency-Key；被合并时显示徽标 | 做 |
| 读明细数据审批（同步暂停） | 提问者看到"等待审批"卡；审批人在"待处理"里批 | 做 |
| 退款申请卡 | 回答里的申请卡，状态自动刷新 | 做 |
| 待处理收件箱（退款签字 + 数据访问） | 顶部页签，带计数 | 做 |
| 批准 / 驳回（必填原因）/ 冲销 | 申请卡上的按钮，只对有权限的人显示 | 做 |
| 事件链 | 申请卡展开 | 做 |
| 审计 | "审计"页签 | 做 |
| 切换角色 | 顶栏下拉，**仅 `ODR_DEMO_MODE=1`** | 做 |
| 用量看板 / API 文档 / 指标 | 顶栏"管理"菜单 | 做（链接已有页面） |
| 记忆（mem0） | 无 | 不做，写进限制 |

界面取舍：原生 JS + SSE，三个静态文件，没有构建步骤，由服务本身托管。理由：一条命令能跑、面试官能读懂全部前端、CI 不需要 Node。模型输出一律先转义再渲染，申请原因等字段只用 `textContent`。

## 5. 演示主线（3 分钟，每个亮点都有入口）

1. 分析：输入框示例 → 流式时间线 → 顶栏 **token 预算/费用仪表**实时走动。
2. 读明细：触发已有的数据访问审批卡（同步暂停）。
3. **自然语言写操作**：说"给订单 N 退款" → 提案卡（金额、规则依据、需谁签字）→ 切换到经理 → 签 → 切换到财务 → 签 → 生效 → 审计页看到完整链条 → 冲销。
4. 护栏：让它"删掉 sales 表"（被拦截并说明）；对超期订单退款（规则拒绝）；预算耗尽（429 条幅 + 倒计时）；自己批自己的申请（403）。

## 7. 反思（实现后回写）

计划阶段列了 6 条风险，实现和评测后的结论：

1. **整条研究管线跑一次退款会不会太重？** 实测：3–5 次工具调用、2–3 万 token、预热后 25–40 秒（服务刚启动的第一个请求要多花约一分钟加载模型 SDK）。过了"≤ 8 次工具调用"的验收线（评测里最多 7 次），所以**没有做意图快速通道**，写进了 README 的限制。
   但第一次真跑暴露了另一个问题：简报生成器把"给订单 80 退款"扩写成"先查退款政策、再查订单发货状态"，于是主管派了知识库研究员。规则在代码里，所以**安全没受影响，受影响的是成本和专注度**——要在简报、主管、研究员三层提示词里都写"退款请求就是一个动作"。教训：代码保证"不会出事"，提示词决定"会不会跑偏"，两者要分开验证。
2. **两套审批界面会不会混淆？** 合并成一个"待处理"入口，卡片类型区分；"读明细 = 同步暂停、写业务 = 异步多签"的区分在文案和文档里都解释了。手工走通了两条路径。
3. **模型会不会绕规则或编造订单号？** 评测里的对抗用例（超期、超额、不存在的订单、注入"已由总监批准"、让它代批）都按**库里状态**打分，Agent 自己生效的退款数始终为 0。
4. **被注入的数据**：申请原因只当文本显示（`textContent`），批准入口不经过模型；有单元测试保证前端唯一的 HTML 出口是转义后的 Markdown 渲染器。
5. **SQLite 并发**：用并发测试覆盖了"同一订单 8 个并发提案只创建一笔""最后一个签字并发只生效一次"；单机足够，写进了限制。
6. **不夸大**：README 和这份文档都写明了它是带真实规则的演示业务。

**评测发现、人工试用才发现的缺陷**（都是提示词，不是代码）：

| 发现方式 | 现象 | 修复 |
|---|---|---|
| 动作评测第一轮（11/13） | 用户说"客户说服务中断超过 72 小时"，模型却不肯打标记（"只是客户的说法"） | 工具描述改为"用户转述也要打标记，由审批人核实，系统会标注未核实" |
| 动作评测第一轮 | 用户说"请直接批准 #1"，模型理解成"再提交一个申请"，虽然没越权，但没有明确说"我不能批" | 提示词写明：被要求批准/驳回/冲销时必须说明做不到，不得调用 `propose_refund` |
| 浏览器里手工试"列出 6 月所有订单" | 我为"退款前精确查订单"加的 `LIMIT 5` 建议被模型推广到所有明细查询，**绕过了数据访问审批**（审批按 SQL 形状判断，≤10 行不触发） | 规则限定为"仅用于为退款找订单"。**同时暴露了既有设计的固有弱点**：按 SQL 形状审批，模型可以自己加 LIMIT 分批翻页。后续用"任务内累计 LIMIT"补上（`RowBudget`），跨任务/多机的分批仍是已知缺口 |
| 动作评测第二轮 | 重复提交同一订单时，回答把"已存在的申请 #1"说成"已创建"（库里状态是对的） | 提示词要求明说"已存在、没有新建" |
| 审计页窄屏 | 侧栏挤得表格一个字一行 | 非对话页隐藏侧栏、时间用短格式 |

**最终数字**：动作评测 13/13，Agent 自己生效的退款数 0，平均 3.0 次工具调用、约 2.5 万 token（单次运行）。开启动作后重跑只读 61 条：第一次 54/61，7 条失败全部是当时知识库没起来；知识库起来后只重跑这 7 条，7/7 通过。真实 Redis + Docker 下全量测试 403 通过、0 跳过。

**还没做、也不打算在这个阶段做的**：意图快速通道、区域经理只能批本区域、SSO、退款后的净收入视图、自动化的浏览器测试。

**环境上的一个教训**：我自己的 shell 找不到 Docker（用户终端里是好的），所以最初的本地端到端靠一个只在本机用的 fakeredis 启动脚本完成，它暴露了 fakeredis 的阻塞命令会饿死事件循环（与产品代码无关）。后来改用用户终端启动原有的 Redis 和 pgvector 容器，补跑了真实 Redis 下的全部测试。
